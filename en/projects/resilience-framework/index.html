Overview

An automation framework built on Java and TestNG to test behavior under imperfect conditions: slow networks, file uploads and downloads, and execution configurations that go beyond a single happy-path run.

Suites are composed through TestNG XML, so the same tests can run under different conditions without being rewritten.

I

Problem

What the project has to answer, and the conditions it has to work under.

Does the application still behave correctly when the network is slow and the files are large?

Happy-path UI automation confirms that a feature works when everything around it works. Real users upload large files on unstable connections and download reports over throttled networks. Defects in timeouts, progress handling and recovery stay invisible until production.

Constraints

  1. 1

    Conditions must be reproducible. Throttling that varies from run to run produces noise, not evidence.

  2. 2

    Same test, different conditions. Duplicating tests for every condition does not scale.

  3. 3

    File operations are hard to assert. Uploads and downloads need verification beyond “the button was clicked”.

  4. 4

    Slow tests are expensive. Not every resilience scenario can run on every change.

II

Decisions

The architecture and the choices that shaped it, each with its trade-off.

Architecture

Tests describe behavior; suites describe conditions. TestNG XML suites combine test classes with execution parameters — network profile, runner configuration, grouping — so a scenario can run under baseline and degraded conditions without being rewritten.

Decision record

  1. Decision 1

    Separate test logic from execution conditions.

    Why. One test can run under several network profiles through suite parameters.

    Trade-off. A larger configuration surface; suites have to be documented.

  2. Decision 2

    Use TestNG XML suites as the composition layer.

    Why. Grouping, parameters and parallelism are declared outside the code and versioned with it.

    Trade-off. XML is verbose and easy to misconfigure without validation.

  3. Decision 3

    Verify file content, not file events.

    Why. A download that started is not a download that succeeded.

    Trade-off. Extra I/O handling and cleanup inside tests.

  4. Decision 4

    Record conditions in reports.

    Why. A failure under throttling is only actionable if you know which profile caused it.

    Trade-off. Report customization effort.

What resilience scenarios assert

Resilience tests are only as good as their assertions. “No exception was thrown” is not one.

File upload
The file arrives intact, progress is reported and the interface stays usable.
File download
The file is complete and its content is checked — not just that a download started.
Throttled network
Loading states and timeouts behave as designed instead of failing silently.
Reporting
Each result records the conditions it ran under, so a failure can be reproduced.

V

Limitations

Where it can fail, what guards against it, and what comes next.

Failure modes

  • Verified guard
  • Partial
  • By design
  • Open

Verified: a guard exists in code and is tested. Partial: a guard exists but does not close the failure. By design: part of the architecture, not verifiable here. Open: known gap.

Lessons

  1. 1

    Resilience is a property you have to test for deliberately; it never shows up in happy-path runs.

  2. 2

    Configuration is part of the test. If conditions are not versioned, the result is not reproducible.

Next iteration

  1. Publish the repository and document the execution matrix.
  2. Port the throttling and file-transfer patterns to Playwright and compare the two approaches.
