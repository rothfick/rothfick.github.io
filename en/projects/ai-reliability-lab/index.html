Overview

Most teams can ship an LLM feature. Far fewer can say, with evidence, whether last week's prompt change, model upgrade or retrieval tweak made it better or worse. This lab is where I build that capability: datasets, evaluators, thresholds and regression gates for RAG pipelines, prompts, structured outputs, tool calls and agents.

It is an engineering lab, not a product. The first concrete harness runs inside Learning OS — typed eval cases, a test-only fake provider, false-mastery and regression checks in the normal test suite. The broader RAG and agent harness is in active development.

I

Problem

What the project has to answer, and the conditions it has to work under.

How do you know whether your AI system improved — or silently regressed?

Traditional software is mostly deterministic: same input, same output, and an assertion either holds or it doesn't. LLM systems are probabilistic. The same prompt can produce different answers, a better answer can be phrased differently, and a regression can hide inside an average that barely moved.

Without evaluation, every change to a prompt, model or retriever is a guess — and the failures that matter most, such as an unsupported claim, a wrong citation or an invalid tool call, are exactly the ones a quick manual check misses.

Constraints

  1. 1

    There is rarely one correct answer. Evaluation has to accept valid variation while still catching real errors.

  2. 2

    Automated judges are models too. An LLM-as-a-judge has its own bias and variance and needs calibration against human labels.

  3. 3

    Retrieval and generation fail differently. A correct-looking answer built on the wrong context is still a defect.

  4. 4

    Evaluation costs time and money. Not every check can run on every commit.

  5. 5

    Averages hide regressions. A small mean improvement can mask a severe failure on a critical slice.

II

Decisions

The architecture and the choices that shaped it, each with its trade-off.

Architecture

The harness treats a model change like any other code change: a versioned dataset, a pipeline under test, a set of evaluators, and an explicit decision against a recorded baseline.

Each case flows through the same path as production — query, retrieval, model, response. Evaluators score the retrieved context and the final response separately, metrics are aggregated per dimension and per slice, and the run ends in a decision instead of a dashboard someone has to interpret.

Decision record

  1. Decision 1

    Treat prompts, models and retrieval settings as versioned code.

    Why. A change you cannot diff and replay is a change you cannot evaluate.

    Trade-off. Process overhead: every experiment needs a recorded configuration.

  2. Decision 2

    Score retrieval and generation separately.

    Why. A good answer from bad context is luck; a bad answer from good context is a prompt or model problem. One combined score cannot tell them apart.

    Trade-off. Retrieval needs relevance labels, which are expensive to create.

  3. Decision 3

    Prefer deterministic evaluators wherever they are sufficient.

    Why. Schema, reference and format checks are fast, free and exact; they leave LLM judges for questions that need semantics.

    Trade-off. Deterministic checks see structure only — a well-formed wrong answer passes them.

  4. Decision 4

    Gate on per-dimension, per-slice thresholds — not one average.

    Why. Critical regressions hide inside small changes to a mean.

    Trade-off. More thresholds to maintain, and more borderline rejections to investigate.

  5. Decision 5

    Keep humans in the loop for calibration.

    Why. An LLM judge is only as trustworthy as its agreement with human labels on a sample.

    Trade-off. Human review is slow; it calibrates the judges rather than grading every run.

III

Implementation

What exists, and how the key parts work or are meant to work — with real excerpts where code is public.

  • –Typed evaluation contract (EvalCase, Evaluator) with six categories — implemented in Learning OS.
  • –Test-only fake model provider, kept out of runtime code by a regression test.
  • –Regression fixtures that pin grading score, misconception detection, schema validity and citation grounding.
  • –False-mastery evals: perfect fake, keyword and model scores across all five dimensions must not yield MASTERED.
  • –Schema-validated structured outputs and usage metadata at the model gateway, with typed errors.
  • –In development: dataset format, retrieval metrics, an LLM judge with calibration, and baseline-vs-candidate reports for RAG pipelines.

Regression thinking

AI development needs the same regression protection as traditional software. A candidate change — prompt, model, retrieval parameters — runs against the same suite as the recorded baseline. The comparison happens per dimension and per slice, and the gate accepts or rejects the change against declared thresholds.

The goal is not a single score. It is a reproducible answer to a practical question: is this change safe to ship?

Evaluator types and their limits

No evaluator type is sufficient on its own. Deterministic checks are cheap and exact but only see structure. LLM judges see meaning but drift and need calibration. Retrieval metrics need labeled relevance. Humans are the ground truth — and the bottleneck. The harness combines them and records which evaluator produced each verdict.

AI quality is not one metric

It is a system. Each part answers a different question, and removing any one of them leaves a blind spot.

Datasets
Versioned cases that represent real usage, including the uncomfortable ones.
Evaluators
Deterministic, model-based, retrieval and human checks — each with a stated limit.
Thresholds
Declared before the run, per dimension, so the decision is not made after seeing the numbers.
Baselines
A recorded reference run. Without one, “better” has no meaning.
Regressions
Per-slice comparisons that surface what a single average hides.
Edge cases
Adversarial inputs, empty retrieval, conflicting sources, prompt injection.
Observations
Failures seen in use become new cases, so the suite grows from reality.

The first harness, inside Learning OS

The evaluator contract already exists in code: typed eval cases with six categories — grading, groundedness, citations, structured output, false mastery and misconceptions. A test-only fake provider lets regression fixtures pin outputs, and a regression test keeps it out of runtime code.

The false-mastery evals assert the most important property of that system: perfect scores from untrusted verifiers can never produce MASTERED.

V

Limitations

Where it can fail, what guards against it, and what comes next.

Failure modes

  • Verified guard
  • Partial
  • By design
  • Open

  • Irrelevant retrieval

    By design

    What it looks like. The retriever returns plausible but wrong passages, and the model answers fluently from them.

    Guard. Context relevance and retrieval recall / precision scored separately from the answer.

  • Hallucination

    Partial

    What it looks like. Claims that no retrieved source supports.

    Guard. Citations must resolve to known source versions (implemented in Learning OS); claim-level groundedness evaluation is in development.

  • Context poisoning

    By design

    What it looks like. A retrieved document carries instructions or false content that steers the model.

    Guard. An adversarial dataset slice with injected instructions; source provenance and allow-lists.

  • Prompt regressions

    By design

    What it looks like. A prompt edit fixes one case and silently breaks others.

    Guard. The full suite runs against the baseline before a change is accepted, compared per slice.

  • Missing evidence

    Verified guard

    What it looks like. The answer may be right, but it cites nothing or cites the wrong source.

    Guard. At least one citation is required by schema and validated against source versions.

  • Invalid structured output

    Verified guard

    What it looks like. JSON that parses but violates the contract — or does not parse at all.

    Guard. Schema validation at the gateway; INVALID_OUTPUT is a typed error, never a silent fallback.

  • Judge drift

    By design

    What it looks like. An LLM judge changes its verdicts when the judge model is updated.

    Guard. Pinned judge model and prompt; periodic recalibration against a human-labeled sample.

Lessons

  1. 1

    The most valuable eval encodes your worst failure. In Learning OS that was false mastery — not grading accuracy.

  2. 2

    Evaluation design starts before the model. If an output has no schema and no citations, there is very little to evaluate.

  3. 3

    Every evaluator needs a stated limit. A check that passes a well-formed wrong answer is still useful, as long as nobody mistakes it for a correctness check.

Next iteration

  1. Publish a small, versioned RAG dataset with relevance labels.
  2. Implement baseline-vs-candidate reports with per-slice deltas.
  3. Calibrate an LLM judge against a human-labeled sample and record the agreement.
  4. Wire the suite into CI as an informational check before making it blocking.
