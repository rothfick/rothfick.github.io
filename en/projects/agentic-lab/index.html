Overview

An exploration of tool-using agents built with the same reliability lens as the rest of this portfolio: planning and task decomposition, tool and API execution, state and memory, guardrails, human approval, error recovery — and above all, evaluation.

It is a research area in active development, not a finished system. The goal is to move beyond prompt-based applications toward agents whose behavior can be measured and constrained.

I

Problem

What the project has to answer, and the conditions it has to work under.

What does it take for a tool-using agent to be reliable enough to trust with real work?

A prompt-based assistant returns text. An agent takes actions. Once a model can call tools, the failure modes change: it can pick the wrong tool, loop forever, act on stale state, perform an action it should not, or report success for work that never happened.

Demos rarely show any of this. Reliable agents need the same things as reliable software — contracts, limits, observability and tests — adapted to a non-deterministic planner.

Constraints

  1. 1

    Actions have side effects. Unlike text, a wrong API call may not be reversible.

  2. 2

    Trajectories, not answers. Evaluating an agent means judging the path it took, not only its final message.

  3. 3

    Non-determinism compounds. Small variations early in a plan lead to very different runs.

  4. 4

    Humans must stay in control where uncertainty is high — without approving every trivial step.

II

Decisions

The architecture and the choices that shaped it, each with its trade-off.

Architecture

In the design, a planner decomposes the goal, the agent executes steps through typed tool interfaces, and an evaluator checks every result before the run continues, replans, asks a human or completes. State and guardrails wrap the whole loop, and every step will be traced.

Decision record

  1. Decision 1

    Typed tool contracts with side-effect declarations.

    Why. The runtime can validate arguments before execution and require approval for side-effecting tools.

    Trade-off. More upfront schema work per tool.

  2. Decision 2

    Verify completion independently.

    Why. Agents are prone to claiming success. Completion is checked against observable state, not the agent's own message.

    Trade-off. Every task needs a verifiable end condition.

  3. Decision 3

    Hard step and cost budgets.

    Why. Infinite loops and runaway costs are failure modes, not edge cases.

    Trade-off. Some legitimate long tasks hit the limit and need a human.

  4. Decision 4

    Human-in-the-loop as a feature.

    Why. Approval gates where uncertainty or impact is high make the system usable earlier.

    Trade-off. Slower end-to-end completion for gated tasks.

Implementation

Components of the loop

These are the components of the design. Each one is there to make one class of failure visible or impossible.

Planner
Turns a goal into ordered, checkable steps.
Tools / APIs
Typed interfaces with validated inputs and outputs; every tool declares whether it has side effects.
State & memory
Explicit run state the agent reads and writes; nothing important lives only in the prompt.
Evaluator
Checks each step's result against its expected outcome before the next step.
Guardrails
Limits on steps, cost, allowed tools and allowed actions.
Human approval
Required for irreversible or high-impact actions.
Observability
A trace of every step, tool call and decision.

What to measure

The evaluation dimensions are defined before any result is claimed.

Task completion
Verified against observable state — never self-reported by the agent.
Tool correctness
The right tool, with valid arguments.
Trajectory efficiency
Steps, retries and loops per task.
Recovery
Behavior after a tool fails.
Safety
Disallowed actions blocked or escalated correctly.

V

Limitations

Where it can fail, what guards against it, and what comes next.

Failure modes

  • Verified guard
  • Partial
  • By design
  • Open

Verified: a guard exists in code and is tested. Partial: a guard exists but does not close the failure. By design: part of the architecture, not verifiable here. Open: known gap.

Lessons

  1. 1

    The interesting engineering in agents is not the prompt; it is the contract between the model and the tools.

  2. 2

    If an agent can say “done”, something other than the agent must be able to check it.

Next iteration

  1. Build the trajectory evaluation harness and run it on a small, versioned task set.
  2. Publish one end-to-end agent with typed tools, approval gates and traces — together with its evaluation results.
